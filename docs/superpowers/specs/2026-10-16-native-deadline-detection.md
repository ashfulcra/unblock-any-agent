# Native declared-update detection

Implement R3 and the first-release detector acceptance through the existing native pilot. Ash's standing instruction authorizes continued safe implementation; choices below are provisional implementation decisions, not additional user preferences. This is a new small subsystem, executed inline with a fresh whole-branch review after implementation.

Workers need a way to declare an expected update without pretending they already need a human decision. A separate listener-scoped process must notice a missed update after the worker ends, preserve the observation, and make the concern recoverable. An unanswered human request stays in Needs you. An uncertain missed update is an investigation; it does not invent a human action or assert that work stopped.

## Selected approach

Use signed immutable expectation/update and overdue-observation records in the existing native annotation. Reuse worker/listener grants, source verification, native CLI, HTTP MCP, browser authentication and managed deployment. A worker-only timer cannot cover the ended-session case; host-specific hooks alone cannot provide the portable baseline. No new OAuth client, database or owner credential in a worker/monitor is introduced.

`work_update` is worker-only. Input is `intent_id`, stable `work_key`, `summary`, `context`, `evidence`, `next_action`, explicit `parents`, `status` (`working`, `completed`, `cancelled`), and `next_update_at` (integer Unix seconds for working; null otherwise). A working deadline must be after server time and within 30 days. An optional `request_id` links an existing owned request; its immutable identity cannot change on later updates. New work identity derives from the authenticated worker, granted environment and work key using a versioned tuple namespace. Existing published pilot identities retain their original ID and environment, history and exact historical retry receipts; they are updated in place after source readback. Work in another environment receives its own identity and cannot use the original environment’s parents. Retain conflicting concurrent revisions; resolve only against explicit reviewed parents. A repeated body/intent remains the same record even after its deadline passes or another update arrives. Completion here closes the expectation, never its associated human request or uncertain actions.

`observe_due` is available to a scoped environment listener or the signed-in owner for an explicit manual check. Input identifies one expectation and its sole current revision. The server checks actual time and scope. Only a working revision whose deadline has passed can receive an observation. Its deterministic body includes that exact revision/deadline and the authenticated observer; repeated checks create the same record. It contains no claim of human need, worker acknowledgment or continuation. Worker credentials cannot make monitor observations; listeners cannot change worker expectations. Historical observations remain after newer updates.

Native attention adds authorized `expectations` with history, current revisions, observations and current concern. Existing requests/grants and their semantics remain intact. Conflicting revisions are visible and cannot be automatically classified as quiet. Associated requests remain separately visible, including unanswered needs and uncertain actions. Native MCP gains `record_work_update`; `recover_work` returns expectations as well as existing requests. Source failure remains unknown, not an empty attention list.

## Independent checks and user experience

Add a check-only `native_monitor` CLI using its own existing listener profile and a private SQLite receipt ledger bound to the exact source/principal/environment/scope. Reopen the profile each tick for explicit renewal. Read native attention, submit due observations, and require exact record readback before marking them persisted. Preserve bodies/receipts through pending writes, source loss and restart. A stale/rejected attempt cannot erase an earlier uncertain write. This process executes no agent command and holds no owner refresh token. It supports one check or a bounded/session loop; it installs no startup service.

The dashboard has a separate Investigate section with work summary/context, declared update time, current evidence, associated question and retained concern history. A manual Check now may observe due expectations using the owner's existing session. Display the distinction between a due expectation and a persisted monitor observation. Do not label a configured monitor or historical observation as a currently healthy background receiver. State that automatic monitoring has not been verified as persistent. A general automatic investigation-to-agent route remains unverified; the concern is addressed to the worker in recovery and stays visible when that route is unavailable.

## Acceptance and limits

- Actual worker declares a short deadline and exits. A separate already-running native monitor notices it without another human prompt. Deployed browser and authorized worker recovery show one persisted investigation; repeat/restart creates no duplicate concern.
- A subsequent worker update preserves the prior concern while removing it from current investigation. A linked unanswered human request remains Needs you. Conflicting updates remain visible until explicitly reconciled.
- Tests cover foreign worker/environment, listener mutation denial, revocation/expiry, server clock, pending/uncertain publication, rejected retries, origin/scope rebinding, historical retry and restart. Existing request/answer/action behavior and both MCP protocol modes remain covered.
- Verify the deployed journey, source/CI/readback and fresh review. This bounded detector does not mark full M3, persistent monitoring, general investigation dispatch, ChatGPT web events or official distribution complete.

Harness milestone M2-3 follows completed M2-2 and precedes full M3. Timeout override: 90 minutes, two milestone retries and two harness-fix attempts. Preserve full M3 attempt2 incomplete and its one remaining retry. Use the existing saved deployment, annotation and development harness.
